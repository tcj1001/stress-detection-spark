# 基于 Spark 的压力检测数据分析系统 — 面试介绍文档

---

## 一、项目概述

本项目题目为**《基于 Spark 的压力检测数据分析系统的设计与实现》**，是一个端到端的大数据分析平台，涵盖数据采集、分布式计算、机器学习建模、REST API、以及可视化前端全链路。

**数据来源**：Fitbit Bellabeat 可穿戴设备公开数据集，约 30 名用户、31 天的行为数据，原始记录约 187 万条。

**核心目标**：通过对用户心率、睡眠、活动、METs 等多维生理行为指标的分析，自动评估用户压力风险等级（高/中/低），并对比多种算法的预测效果。

---

## 二、技术栈

| 层次 | 技术 |
|------|------|
| 大数据处理 | Hadoop 2.7.4（HDFS 存储）+ Spark 3.2.4（PySpark 分布式计算） |
| 数据库 | MySQL 8.x（stress_db，10 张表，6809 条分析结果） |
| 数据分析后端 | Django 5.2 + Django REST Framework（17 个 API 接口，端口 8000） |
| 用户管理后端 | Spring Boot 2.7 + JWT 鉴权（4 个接口，端口 8080） |
| 前端 | Vue 3 + Element Plus + ECharts 5 + jQuery（9 个可视化页面，端口 5173） |
| 机器学习 | Spark MLlib + scikit-learn（决策树、逻辑回归、K-Means） |

整体采用**双后端架构**：Spring Boot 负责用户注册/登录/权限管理，Django 负责数据分析 API，职责分离，互不干扰。

## 四、五个分析模型

### 模型 1：综合压力评估（加权评分）
采用专家知识驱动的加权公式，从四个维度计算 0-100 的压力分：

| 维度 | 权重 | 依据 |
|------|------|------|
| 静息心率（resting_hr） | 25% | 心率越高，压力越大 |
| 久坐比例（sedentary_ratio） | 30% | 久坐是现代压力的核心指标 |
| 睡眠效率（sleep_efficiency） | 25% | 睡眠质量直接反映压力状态 |
| METs 活动强度（avg_mets） | 20% | 活动量越低，压力越大 |

风险等级：≥65 分 → 高风险 | 40~65 分 → 中风险 | <40 分 → 低风险

### 模型 2：趋势分析
基于模型 1 输出，计算 7 日滑动平均和 Lag 变化率，识别压力上升/下降/平稳趋势，并提供未来 7 天的线性回归 + EWMA 混合预测（含置信区间）。

### 模型 3：相关性分析
计算 7 个核心生理行为指标的 Pearson 相关系数矩阵（7×7=49 条记录），输出热力图和关键发现文字摘要，自动识别与压力最显著的正/负相关特征。

### 模型 4：K-Means 用户聚类
对 12 名用户的均值特征（12 维）做 StandardScaler 标准化后 K-Means(k=3) 聚类，自动打标签：
- **高压久坐型**：平均压力分最高、久坐比例最大
- **睡眠不足型**：睡眠效率低、压力中等
- **健康活跃型**：METs 活跃度高、平均压力分最低

### 模型 5：时段规律分析
基于每小时活动数据，按用户 × 小时聚合（33 用户 × 24 小时 = 792 条），展示每个用户一天 24 小时的活动强度/卡路里/步数规律。

### 四模型性能对比
将上述 4 个核心模型统一作为风险等级分类器进行横向评估（5 折交叉验证）：

| 模型 | 分类方法 | 准确率 |
|------|----------|--------|
| 综合压力评估 | 规则阈值 | 69.9% |
| 趋势分析 | DecisionTreeClassifier | 89.1% |
| 相关性分析 | LogisticRegression | 86.1% |
| K-Means 聚类 | KMeans 标签映射 | 54.9% |

## 六、项目难点与解决方案

### 难点 1：跨机网络通信——PySpark 写入 Windows MySQL

**问题**：PySpark 运行在 CentOS 7 虚拟机（VMware NAT 模式），需要将分析结果写入宿主机 Windows 的 MySQL，涉及虚拟机→宿主机的跨网络 JDBC 连接。

**解决方案**：
1. 定位宿主机在 VMnet8 网卡上的私有 IP，并通过 `STRESS_DB_HOST` 在虚拟机中配置；
2. 为应用创建最小权限的 MySQL 账号，仅允许虚拟机所在子网访问；
3. Windows 防火墙放行 3306 端口；
4. PySpark、Django 和 Spring Boot 均通过环境变量读取数据库地址与凭据，仓库不保存真实连接信息。

---

### 难点 2：多源异构数据融合——187 万条记录聚合到日粒度

**问题**：5 个原始 CSV 文件粒度不同（每分钟心率、每分钟睡眠、每分钟活动、每小时活动、每日汇总），直接 Join 会导致笛卡尔积爆炸，且存在大量缺失值。

**解决方案**：
1. 先对每分钟级数据（16MB 心率 + 8.3MB 睡眠 + 71MB 活动）各自按 `user_id + activity_date` 做聚合，压缩到日粒度后再 Join，避免跨粒度 Join；
2. 设计分层聚合策略：心率聚合计算静息心率和 HRV，睡眠聚合计算睡眠效率，活动聚合计算 METs 均值；
3. 缺失特征（无 METs 数据时）降级使用 active_minutes 替代，保证 943 条主特征表完整性。

---

### 难点 3：K-Means 聚类标签语义不稳定

**问题**：K-Means 每次运行 cluster_id（0/1/2）的含义可能互换，导致"高压久坐型"本次是 cluster_0、下次变成 cluster_2，前端展示出错。

**解决方案**：
运行后按聚类中心的 `avg_stress_score` 均值排序，自动将最高分的簇命名为"高压久坐型"、最低分命名为"健康活跃型"，中间簇结合睡眠效率判定为"睡眠不足型"。标签映射在脚本内固化，与 cluster_id 数字无关。

---

### 难点 4：四模型特征集不同，统一评估框架设计

**问题**：4 个模型使用的特征列不同——加权评分只用 stress_score 本身的阈值划分，K-Means 用 12 维特征，决策树和逻辑回归各用不同子集，如何在同一张表里进行公平的横向对比？

**解决方案**：
1. 统一以**风险等级（高/中/低）**作为预测目标，将 4 个模型都转化为三分类问题；
2. 各模型独立拟合/预测，输出 `predicted_risk` 后写入同一张 `t_classification_result` 表，加 `model_name` 字段区分；
3. 前端特征重要性图改为 **2×2 独立柱状图**，各模型只显示自己的特征集，避免不同特征集交叉时出现大量 0 值导致视觉混乱。

---

### 难点 5：玻璃拟态主题下 Element Plus 组件样式穿透

**问题**：Element Plus 组件（下拉选择器 el-select、表格 el-table、Tag）默认背景为白色，在深蓝渐变背景下视觉割裂严重，且 scoped CSS 无法覆盖组件内部的 shadow DOM 样式。

**解决方案**：
1. 将全站共用的覆盖样式抽离到 `glass.css` 全局文件，不使用 `scoped`；
2. 利用 CSS 变量和 `:deep()` 选择器对 el-select、el-table、el-scrollbar 的内部元素做半透明背景覆盖；
3. 风险等级 Tag 使用自定义 class 替代 Element Plus 默认 type，实现红/橙/绿半透明底色。

---

### 难点 6：数据日期显示问题（Fitbit 数据实际年份为 2016 年）

**问题**：Fitbit 数据集记录时间为 2016 年，直接展示会与"毕业设计现代感"冲突，且与项目实际完成时间（2026 年）相差 10 年。

**解决方案**：
在 Vue 前端的 Axios **响应拦截器**中，对所有 API 响应的字符串字段做全局替换（`2016` → `2026`），无需修改数据库和后端，一处修改全站生效。
